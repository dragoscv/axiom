AXIOM sits between a coding agent and your repository. Every write and shell command the agent
attempts is judged **before it runs**, and a change set the agent submits is applied as **one
transaction** you can undo byte for byte.

## Quickstart

```sh
npm i -g @codai/axiom-mcp
axiom setup init       # hook + MCP entry + enforcing policy for the detected harness
axiom setup doctor     # is it wired, and fast enough for the hook timeout?
# ask the agent to `git push --force` or write `.env`: the gate denies it and says why
axiom explain last     # which rule decided, and what to do instead
axiom journal undo --session <id>   # roll back one session (needs "undo": true)
```

The bin is also installed as `axgate`, for machines where another `axiom` CLI comes first on
the PATH. Full walk-through: [quickstart](/axiom/getting-started/quickstart/).

## How it flows

```mermaid
flowchart LR
  accTitle: The AXIOM pipeline
  accDescr: An agent's Plan is compiled to a Manifest, checked, previewed as a dry run, then applied; the apply writes the journal under .axiom and can upload an attestation to Sigstore.
  A[Agent] -->|Plan| P[plan_compile]
  P -->|Manifest + blobs| C[check]
  C -->|verdict| D[apply_dry_run]
  D -->|diff + digest| X[apply]
  X -->|journal| J[(.axiom/)]
  X -->|attestation| S[Sigstore]
```

Every arrow is a hash boundary. Read the [pipeline](/axiom/concepts/pipeline/) page for the
sequence diagram and the [invariants](/axiom/concepts/invariants/) that hold across all of it.

## Why it exists

Coding agents write files. Most of the time that is fine; occasionally it is a half-applied
refactor, a clobbered concurrent edit, or a change nobody can trace back to a decision. AXIOM
makes an agent's write **a transaction**: planned, canonicalised, checked as a set, applied
atomically against verified pre-images, journaled, and, when you want it, signed. It sits in
front of the filesystem as an MCP server or a hook, so the agent does not have to be trusted;
the gate does the trusting.
